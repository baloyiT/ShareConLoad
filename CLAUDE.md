# PROJECT: ShareConLoad

## SYSTEM OVERVIEW

ShareConLoad is a global logistics marketplace that connects:

- Customers shipping goods internationally
- Operators providing shared container space

The platform enables:
- Container discovery
- Booking of space (CBM-based)
- Goods declaration
- Shipment tracking
- Staged payment collection (Paystack)
- Operator payout management
- Dispute & claims handling
- Customs event tracking
- Cargo release authorization
- Support ticket management

This is NOT a generic app.
It is a structured logistics system with strict data and workflow rules.

## BUSINESS RULES (CRITICAL)

### Containers
- Must have origin + destination (country + city)
- Must track:
  - total_capacity_cbm
  - available_capacity_cbm
- available_capacity_cbm <= total_capacity_cbm

---

### Bookings
- Must reference container
- Must include:
  - total_cbm
  - total_price
- Cannot exceed available capacity

---

### Shipment Items
- One booking can have multiple items
- Must include description and declared_value

---

### Goods Declaration (MANDATORY)
- Every booking MUST have a declaration
- agreed_terms must be TRUE
- Booking is invalid without declaration

---

### Booking Status Lifecycle
Only allow:

pending → confirmed → loaded → in_transit → delivered

(cancelled allowed from any stage)

---

### Payment Lifecycle (CRITICAL)

Three stages are auto-generated by DB trigger on every booking insert:

| Stage | Amount | Trigger |
|---|---|---|
| deposit_20 | 20% of total_price | Booking creation — due within 24h |
| pre_departure_50 | 50% of total_price | 7-day departure notification |
| final_release_30 | 30% of total_price | Cargo arrival — required before release |

Rules:
- Booking progression is blocked if the required payment stage is not `paid`
- Payment records have status: `pending` → `paid` → `refunded` (or `failed`)
- Only one stage is payable at a time (in order)
- Refunds are never automatic — require admin approval

---

### Operator Payout Eligibility

A payout may only be triggered when ALL of the following are true:
- Corresponding customer payment stage is `paid`
- `operator_profiles.payout_enabled = true`
- `operator_profiles.payout_hold = false`
- `operator_profiles.paystack_recipient_code` is set
- No active dispute on the booking
- Refund window has expired (48h for Stage 1)

Payout amounts = gross minus platform commission (tiered by booking value).

### Multi-Currency

The platform supports multiple currencies: USD, ZAR, GHS, NGN, KES, GBP, EUR, XOF, EGP.

- `containers.currency_code` — the operator's pricing currency (FK → `fx_rates`)
- `containers.price_per_cbm_usd` — USD equivalent for cross-currency display and filtering
- `fx_rates` table — exchange rates to USD, manually updated by admin
- **USD is the normalising currency** for commission tier lookups: `booking.total_price` is converted to USD via `fx_rates.rate_to_usd` before determining which tier applies
- Commission tier thresholds in `platform_commission_config.tiers` are always in USD

---

### Cargo Release Conditions

`cargo_release_authorizations` must have ALL four conditions set to `true` before release:
- `final_payment_confirmed`
- `customs_cleared`
- `consignee_verified`
- `operator_confirmed`

Only admins can toggle these conditions and authorize release.

## DATABASE MIGRATIONS

**Every schema change MUST be a SQL file** — no exceptions.

Rules:
- Create a new file in `supabase/migrations/` for every DDL change (tables, columns, indexes, RLS policies, functions, triggers, types, storage buckets)
- Naming: `YYYYMMDD_NN_short_description.sql` (e.g. `20260514_17_operator_compliance_gate.sql`)
- Write migrations to be idempotent: use `create table if not exists`, `add column if not exists`, `create index if not exists`, `on conflict (id) do nothing`, `drop policy if exists` before recreating policies
- Wrap `create type` and `create policy` in `do $$ begin … exception when duplicate_object then null; end $$` blocks
- Never apply schema changes by pasting SQL directly without also saving it as a file
- Commit the file immediately after creating it
